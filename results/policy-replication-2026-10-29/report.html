What to improve next

The P100 equal-work records show inefficient admissions: in pressure cells, adaptive makes 20 and 19 native admissions versus simple admission's 18, but still gets the same 18 hits. In cancellation cells it admits 24 and 26 snapshots versus 18, yet gets only 12 and 13 hits versus 15. More cache work does not necessarily buy more reuse.

Timing variability also matters. P100 generation and prefill components vary across blocks despite fixed token counts. The entire elapsed-time gap cannot be attributed to the admission algorithm. The observed gap is enough to reject a proven adaptive win; it is not a precise causal estimate of policy overhead.

  1. Keep simple admission as the default benchmark to beat. Separate cache-control and restoration time from prefill/generation, and record CPU scheduling, threads, GPU clocks and utilization on future runs.
  2. Investigate replacements that cause extra exports without a net hit gain. Develop a conservative admission rule using only signals available at decision time; cancellation labels known after the fact are not valid prediction inputs.
  3. Freeze a new realistic trace workload and a meaningful win threshold before evaluating changes. Compare simple admission, TTL, idleness and recomputation; include end-to-end latency, constrained resource memory and answer preservation.

Do not rent another GPU merely to repeat this fixture. These P100 results already answer the main baseline question. A new paired run is useful after instrumentation or a candidate policy change, followed by an untouched evaluation workload.

Controls, audits and limits

  • Four P100 runs pass independent artifact, score and accounting audits: two smoke runs of 48 sessions each and two full runs of 2,592 sessions each. Each full mode has 108 blocks and 5,184 events. The test log reports 512 passed, 11 skipped and 89 subtests passed. The XML includes subtests, so its total must not be presented as 601 ordinary tests.
  • P100 source label: b91ebb37ead55d21dabe23ef0311ae2a9d2dc697; RTX: ca6f6feaaf7faef4b942bd37d78ee29ded99a27a. All 25 recorded benchmark source hashes match. Intervening repository changes concern CI, tests, documentation and saved evidence.
  • Same pinned Qwen2.5-0.5B-Instruct model digest, prompts, input tokens, expected answers, schedules, budgets, policy order and benchmark arguments apart from paths. Contexts 512/2048; 24 cases; 3 repeats; 24 forced steps in equal_work and at most 24 output tokens in free_generation.
  • Frozen equal-work continuations match for 47/48 context-case pairs. At 512/case-0002, the 24-step sequence differs from the eighth token onward, after EOS at the third token. Within each system all policies use identical forced inputs; cross-system token identity is incomplete. The full free-generation recompute answers match.
  • Torch 2.7.1 uses CUDA 12.6 on P100 and CUDA 12.8 on RTX; operating systems differ. CPU, PCIe and driver settings are not matched or fully documented. The P100 folder lacks the later runtime sidecar, so CPU affinity, cgroup quota and thread settings cannot be reconstructed. This is not a GPU-only causal comparison.
  • The supplied P100 folder has per-run manifests but no outer suite manifest. The preserved copy has a new import receipt, which records the files as received and does not retroactively attest their origin. Artifact audits establish internal consistency, not an independent signature or physical-execution proof.
