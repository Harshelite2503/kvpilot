28 October 2026 · Tesla P100-PCIE-16GB · Qwen2.5-0.5B-Instruct

A useful admission-control signal; no demonstrated GPU-memory saving

Adaptive eviction took 25–52% less full-session time than this implementation of fixed INT4. The more informative native-cache comparison shows 6.4–7.9% less time in cancellation scenarios, with the same observed answers and effectively the same retained-payload peak.

Audit passed. The independent validator checked 2,160 sessions, 4,320 events and 90 blocks. All 24 recorded source hashes match commit fac2ed29beb602b67725417b6b2f384a14ea5aa7. The successful smoke archive also validates. This is an audit of records, not an independent GPU rerun.

What the policy actually did

Across its 432 started sessions, adaptive eviction chose 222 native snapshots and 210 recomputations. It never chose INT8 or INT4. Adaptive exact chose native snapshots for all 432 sessions. Therefore these results evaluate admission and eviction decisions, not successful adaptive lossy compression.

Under pressure, adaptive avoids serializing states that would displace useful existing states. Under cancellation it also retains more states that later resume. At 2,048 tokens with cancellation, average pause cost falls from 57.28 ms to 17.54 ms per started session; restore/recompute cost falls from 336.10 ms to 296.06 ms. Generation is essentially unchanged.

A crucial baseline is missing: store a native snapshot only when free capacity exists; otherwise recompute, without evicting anyone. Replaying only the recorded sizes and event order predicts the same 6 hits per pressure repeat and 5 hits per cancellation repeat as adaptive. In cancellation this simple rule would create 6 snapshots instead of adaptive’s 7 per repeat. This is an accounting counterfactual, not a measured speed result. The present experiment does not establish that adaptive forecasting beats this simple rule.

Both adaptive policies and native caching match recomputation’s exact generated tokens on all 396 answered observations each. INT4 matches on 171/396. None of the 1,980 total responses was truncated. These are observed baseline agreements, not a general quality guarantee or an external correctness audit of the model runner.

Do not turn format failures into factual-error claims. At 2,048 tokens in the roomy scenario, 11 of the 12 distinct baseline-correct → INT4-failed cases retain the correct number but add prose, violating the explicit number-only instruction. One changes port 6627 to service identifier 79947. At 512 tokens, genuine errors include sum 10 → 12 and pager code 7285 → team_23209. INT4 also fixes some baseline errors.

Generation length contributes to the speed ratio: 2,048-token roomy INT4 produces four times as many output tokens (1,092 vs 273); mean generation takes 444.63 ms vs 133.51 ms. Full-session timing correctly includes this difference, but the 2.10× ratio cannot be attributed entirely to cache mechanics. Native comparisons have identical outputs and avoid this confound.

CUDA peak allocated memory is identical across all five policies: 977.932 MiB at 512 tokens and 1,044.450 MiB at 2,048. Maximum reserved memory across repeats is 1,112 MiB for every policy and condition; individual early blocks report 1,102 MiB. CPU payload compression therefore demonstrates no GPU-memory saving here. Active states are restored to native precision; compression runs after full native export and does not reduce that initial device-to-host copy.

At 2,048 tokens under pressure, adaptive’s mean gain over native is only 1.0%, one of three repeats is slower, and descriptive p95 resume time is worse (637.6 vs 555.5 ms). Report this alongside the favorable cancellation result. Process RSS is sampled and affected by allocator history; it is not a clean per-policy memory comparison.

What to claim, and what to test next

Defensible wording: “In a controlled P100 experiment with our owned cache and a 0.5B model, eviction-aware admission reduced mean full-session time by 6.4–7.9% against always-store-native LRU under cancellation, with identical observed outputs and approximately equal retained-payload memory. This needs confirmation against simpler admission rules and unseen workloads.”

  1. Add the native-only admission rule above as a measured baseline; keep the current results and policy frozen.
  2. Freeze fresh workload seeds and new schedule families before execution: variable session lengths, reuse probabilities, cancellation rates and capacity levels. The current full run repeats the four smoke questions and is development evidence.
  3. Use a fixed-generation-work timing companion to isolate cache overhead, alongside the existing free-generation answer-quality test. Retain the strict rubric and separately report reviewed semantic/value errors.
  4. Run on the free P100 first. Require a repeatable gain over the best simple quality-preserving baseline under the same capacity limit, with acceptable tail latency, before paying for the 3090 or making a broad performance claim.
