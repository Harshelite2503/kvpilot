## Measured result

The table compares **adaptive eviction** with fixed INT4 and always-store-native LRU. Percentages are reductions in mean full-session time per started session, including initial prefill, pause, restoration/recomputation, generation and cancellation work. Positive means faster. Stored memory is retained serialized payload, not GPU/process memory.

| Context target | Scenario | Adaptive ms | Less time vs INT4 | Less time vs native | Peak payload vs INT4 |
|---:|---|---:|---:|---:|---:|
| 512 | Roomy | 260.30 | 39.0% | -0.3% | 3.74× |
| 512 | Pressure | 323.01 | 25.4% | 3.8% | 1.07× |
| 512 | Cancellation | 268.09 | 33.9% | 6.4% | 1.07× |
| 2,048 | Roomy | 772.47 | 52.4% | 0.1% | 3.76× |
| 2,048 | Pressure | 1,110.28 | 31.1% | 1.0% | 1.08× |
| 2,048 | Cancellation | 941.90 | 35.9% | 7.9% | 1.08× |

Cancellation improvements over native are positive in all three paired repeats at each context length. Roomy native and adaptive essentially tie. At 2,048 under pressure, one adaptive repeat is slower and descriptive p95 resume TTFT is **637.6 ms versus native's 555.5 ms**. Three repetitions do not establish formal significance or generalization.

CUDA peak allocated memory is identical across all five policies: **977.932 MiB at 512** and **1,044.450 MiB at 2,048**. No GPU-memory saving was demonstrated. Native and adaptive stored memory is effectively equal; the pressure/cancellation difference is only 12,288 bytes. CPU compression happens after full native export, so smaller retained payloads do not reduce that initial device-to-host copy.

## What caused the difference

Adaptive eviction selected **222 native snapshots and 210 recomputations**, with no INT4/INT8 choices. Adaptive without eviction pricing selected native for all 432 sessions. The observed mechanism is admission control that avoids wasted snapshots, not improved lossy compression.

Under pressure, adaptive and native have the same 18 hits across three repeats, but adaptive avoids 54 snapshot admissions that the native baseline eventually evicts. Under cancellation, adaptive has 15 hits versus native's 9. At 2,048 with cancellation, mean pause cost falls from 57.28 to 17.54 ms per started session, and mean restore/recompute work from 336.10 to 296.06 ms.

A **not-yet-measured baseline** is decisive: store native only if there is free space; otherwise recompute, never evict. Replaying the exact event order and sizes predicts the same 6 pressure hits or 5 cancellation hits per repeat as adaptive. For cancellation it would require 6 rather than 7 snapshots per repeat. This is a counterfactual accounting calculation, not a runtime measurement. The existing run does not establish that adaptive forecasting outperforms this simple rule.

## Answer quality and timing confounds

Both adaptive policies and native match recomputation's exact output tokens on **396/396 answered observations each**. There are only **24 distinct base questions**, reused across two contexts, three scenarios and three repeats. Outputs do not vary between repeats; no responses were truncated. The full fixture includes the four smoke questions and is development evidence, not a clean unseen holdout.

| Context / scenario | Adaptive/native/recompute correct, repeats removed | Fixed INT4 correct |
|---|---:|---:|
| 512 roomy | 13/24 | 10/24 |
| 512 pressure | 13/24 | 11/24 |
| 512 cancellation | 10/18 | 9/18 |
| 2,048 roomy | 17/24 | 5/24 |
| 2,048 pressure | 17/24 | 7/24 |
| 2,048 cancellation | 12/18 | 5/18 |

Keep the frozen strict score, but explain it: at 2,048 roomy, 11 of 12 baseline-correct → INT4-failed distinct cases retain the correct number but add prose, violating the requested number-only format. One changes port `6627` to service identifier `79947`. At 512, genuine content errors include sum `10` → `12` and pager `7285` → `team_23209`. INT4 also repairs some baseline mistakes.

At 2,048 roomy, INT4 generates **1,092 tokens versus adaptive/native's 273**. Mean generation takes **444.63 versus 133.51 ms**. Part of the 2.10× full-session ratio is changed answer verbosity. Codec overhead is also substantial, but a fixed-work companion experiment is needed to isolate it. Native comparisons have identical outputs and avoid this confound.

## Reproduce the audit without a GPU

From the repository root, extract into fresh scratch directories. These commands consume the checked-in, hash-recorded archives:

```bash
KVPILOT_AUDIT_DIR="$(mktemp -d)"
tar -xzf results/p100-2026-10-28-full/run.tar.gz -C "$KVPILOT_AUDIT_DIR"
python3 scripts/validate_p100_results.py "$KVPILOT_AUDIT_DIR/run"
python3 results/p100-2026-10-28-analysis/analyze.py \
  "$KVPILOT_AUDIT_DIR/run" . "$KVPILOT_AUDIT_DIR/analysis"
```

The analysis narrative is bound to this run's artifact-manifest digest. Its source cross-check currently requires a checkout whose 24 recorded source files match the benchmark; use the measured revision in a separate checkout if those files later change. The independent archive validator does not require a GPU or inference dependencies. For future record publication, see [recording results from the VM](recording-results.md).

The [next-experiment plan](next-experiments.md) prioritizes the missing baseline, unseen session families, equal-work timing and customer evidence. This record supports a narrow 6–8% admission-control observation; it does not support a general 2× faster / lower-VRAM claim.
